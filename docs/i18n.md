# Internationalization

## The Need

The product is Spanish-first but must be translatable.

## The Goal

Every user-facing string comes from a dictionary, and the URL carries the locale (`/es/...`, `/en/...`).

## The Reason

Next.js's own App Router pattern (a `[lang]` segment, dictionaries, and a locale redirect) with no i18n library. It covers what we need and adds no dependency.

## The Implementation

- **Routing:** all routes live under `app/[lang]/`. `proxy.ts` redirects any path without a locale to the best match for the browser's `Accept-Language`, defaulting to `es`. Next.js 16 renamed Middleware to Proxy; `proxy.ts` is that file.
- **Dictionaries:** `src/shared/i18n/dictionaries/{es,en}.json`. `es.json` defines the `Dictionary` type, and a unit test fails if the files' keys differ.
- **Loading:** `app/[lang]/layout.tsx` calls `getDictionary(lang)` on the server and passes the result to `DictionaryProvider`.
- **Usage in components:** `const { onboarding } = useDictionary()`. Navigate with `useLocalizedRouter().replace("/login")`, which keeps the locale.
- **Backend errors:** the API returns stable codes; `errorMessage(dictionary.errors, code)` turns a code into text. Add new codes to both dictionaries.
- **Adding a language:** add the JSON file, then the locale in `config.ts` and `get-dictionary.ts`.

## Known gaps

- No language switcher in the UI; the locale changes by URL or browser language.
- Dates in `<input type="date">` follow the browser's locale, not the URL's.
